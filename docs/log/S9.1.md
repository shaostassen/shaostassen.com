# S9.1 — shaostassen.com live on Vercel

Status: done · Started: 2026-07-25 · Shipped: 2026-07-25

## What happened

Agent side: added apex + `www` to the Vercel project, issued the
certificate, set the `www` → apex redirect, flipped `SITE_URL`, rebuilt,
verified. Human side: the DNS records (per plan §14).

## The interesting part — two hosted zones

`vercel domains inspect` asked for `A 76.76.21.21`, but before handing
over instructions I checked the actual DNS state and found:

- the registrar is Amazon Registrar; the domain delegated to four AWS
  nameservers that **did** answer authoritatively;
- the delegated zone was **empty** (NS + SOA only, serial 1);
- the AWS account reachable from this machine had **zero** hosted zones.

So the zone being served lived in a different account. Shao added the
records correctly, but into a *second* zone for the same name (`ns-241…`
set) — invisible to the world because the registrar delegated to the
`ns-103…` set. Diagnosed by querying each authoritative NS directly:
records present on his zone's servers, absent on the delegated ones.

Resolution: he repointed the registrar's nameservers at his zone.

**Typo caught in the new delegation:** the registry listed
`ns-1657.awsdns-20.co.uk` where the zone's server is
`ns-1697.awsdns-20.co.uk`; `ns-1657` does not respond. Three of four
resolve so the site works, but ~25% of lookups hit a dead server and
stall until the resolver retries. Flagged for Shao — **still outstanding
at ship time**.

## Verification

- apex + `www` resolve to 76.76.21.21 (public resolvers) ✅
- `https://shaostassen.com` → HTTP/2 200, Let's Encrypt cert
  `CN=shaostassen.com`, expires 2026-10-23 (auto-renews) ✅
- `www` → 308 redirect to apex, so one canonical host ✅
- Rebuild confirms every absolute URL derives from `SITE_URL`: og:url,
  og:image, sitemap `<loc>`s, robots `Sitemap:`, JSON-LD `url` ✅

Note: this machine's resolver cached the earlier negative answer, so
local `curl`/`dig` looked broken while the site was fine — verified with
`--resolve` and public DNS instead. Not a site issue.

## The story

PLAN §11: "the 'of course this is an engineer's site' moment." A small
in-browser demo — client-only, static-export-safe, accessible, performant,
mobile-friendly, on the landing page or a project detail, degrading
gracefully.

This is the last story before the site is feature-complete, and the one
with the most room to go wrong: it is the only piece of the site that is
interactive for its own sake, so it has to earn the bytes.

## Approaches considered

**What to simulate**

- *(a) PID step response with actuator saturation and integrator
  anti-windup.* **Chosen.** One slider move produces a visible change in
  overshoot, so the interaction teaches something in under a second. It is
  also already claimed elsewhere on the site: Fast Robots tags `PID` and
  `LQR`, and Huey's case study names `Anti-windup` outright. A demo of a
  claim the site already makes is evidence; a demo of something unrelated
  is decoration.
- *(b) Kalman filter — noisy measurement vs. filtered estimate.* Closer to
  the Fast Robots headline, but it needs noise. Real randomness makes the
  server and client renders differ, which either breaks hydration or forces
  the whole thing client-only and empty without JS. A canned noise array
  fixes that but costs bytes and reads as a canned animation.
- *(c) Grid-based Bayes localization.* The most distinctive of the three
  and the most expensive: a pose grid, a beam sensor model, and a heavy
  mobile layout. Wrong ratio of payload to insight for a portfolio.

**Where it lives**

- *(a) Landing page.* Maximum reach — but the landing page is the site's
  weakest performance route (93 against a floor of 90, measured in S7.3),
  and it already carries the hero portrait and the full-bleed band. Putting
  the site's only interactive component on its tightest budget spends
  margin that is not there.
- *(b) The Fast Robots case study.* **Chosen.** PID is genuinely what that
  project did, so the demo lands as evidence inside the argument rather
  than as an attraction on the front page — which is the site's own stated
  principle ("every claim is backed by a project, a number, or a link").
  That page measured 96, so there is real headroom. The component is
  self-contained, so moving it to the landing page later is an import and
  a line of JSX.

## Architecture

- `src/components/demo/PidLab.tsx` — one `"use client"` component, **no new
  dependencies**. Nothing is added to `package.json` by this story.
- **Deterministic simulation.** A second-order plant (mass with viscous
  damping), `ẍ = (u − b·ẋ) / m`, driven by a PID with a clamped integrator.
  Fixed `dt`, fixed horizon, no `Math.random`, no `Date` — so the server
  prerender and the client hydration compute byte-identical output. This is
  what makes graceful degradation real rather than claimed: the default
  curve is in the exported HTML, and a visitor without JS sees a genuine
  chart with genuine numbers, just no sliders.
- **SVG, not canvas.** A polyline over ~200 sampled points. Canvas would
  need an effect, a ref, a device-pixel-ratio dance, and would render
  nothing server-side. SVG is inspectable, themeable with tokens, and free.
- **No animation.** The trace is recomputed, not drawn. That sidesteps
  `prefers-reduced-motion` entirely instead of gating it, and keeps the
  main thread quiet.
- **Controls are native.** `<input type="range">` and `<input
  type="checkbox">` with real `<label>`s — keyboard-operable and
  screen-reader-correct for free. No custom slider.
- **Traces are scope channels:** position on `accent` (CH1), control effort
  on `accent-2` (CH2), setpoint dashed in `muted`, saturation band shaded.
  No new colors.
- **MDX component mapping.** `compileMDX` gets a `components` map so
  `fast-robots.mdx` can place `<PidLab />` itself. The demo is content for
  that project, not a template feature bolted onto every case study.

Scope held down deliberately: three gain sliders plus an anti-windup
toggle. Actuator saturation is **fixed** and drawn rather than made a
fifth control — high `Ki` against a fixed limit already tells the windup
story, and four controls fit a 375px column where five crowd it.

## Risks

- **Honesty.** This is a generic second-order plant, not the robot's
  measured dynamics. The caption must say so plainly. Inventing plant
  parameters and presenting them as the robot's would violate the sourcing
  rule in `project-mdx` as surely as inventing a metric would.
- **Hydration mismatch** if any non-determinism creeps into the sim.
  Guarded by the no-RNG/no-clock rule and by a test that asserts zero
  console errors on the case-study page.
- **Performance.** The case study has headroom (96), but this adds the
  page's first client JS. Watched by the widened S7.3 Lighthouse config,
  which already audits `/projects/fast-robots`.
- **Accessibility = 100 is a hard gate.** A chart is the classic way to
  lose it. Mitigation: the SVG is `role="img"` with a summarizing label,
  and the real accessible payload is the metrics list plus a debounced
  polite live region — announced after the user stops dragging, not on
  every input event.

## Decisions

- **The plant changed mid-build, for honesty.** The first version was a
  second-order mass-damper. Writing the prose exposed the problem: that
  plant is type-1 in position, so proportional control alone already drives
  steady-state error to zero (measured 0.001). The copy I had written —
  "add Ki to erase steady-state error" — was the textbook line and was
  simply **false for the plant I had built**. Swapped to a first-order lag,
  `ẋ = (K·u − x)/τ` with `K = 2`, `τ = 0.35 s`, where P-only leaves a real
  residual (0.200 at Kp 2, 0.048 at Kp 10) that only Ki closes. The demo
  now demonstrates the sentence next to it.
- **`K = 2`, not 1.** At unity gain the steady state needs `u = 1`, which is
  exactly the saturation limit — the actuator would have no authority left
  for the transient. A DC gain of 2 puts steady state at `u = 0.5` and
  leaves real headroom, so saturation still bites during the step (which is
  what makes windup visible) without the loop living on the stop.
- **Defaults are a good tune, not a dramatic one**: `Kp 2, Ki 8, Kd 0.05`,
  anti-windup on → 1% overshoot, settles in 0.41 s, zero steady-state
  error. First impression should be a loop that works; the prose tells you
  how to break it.
- **Fixed axes.** Dragging a slider changes the curve, never the frame, so
  two tunes can be compared by eye. `Y_MAX` is not a guess: a sweep over
  the whole Kp/Ki/Kd/anti grid puts the worst reachable peak at 1.656, so
  the bound is 1.75.
- **Horizon 2 s.** With settling times of 0.3–1.0 s, the original 6 s put
  all the action in the first sixth of the plot.
- Placement on the case study rather than the landing page (rationale
  above) — and the landing page's score is unchanged at 94 as a result,
  while Fast Robots went 96 → 97.

## Gotchas

- **An unfiltered derivative at `dt = 2 ms` destroys the loop.** The first
  build computed `d(error)/dt` directly. At this step size the D term
  reached ~6 against a P term of ~4 and inverted the control signal on the
  second step: the output never left zero, and the metrics read "does not
  settle" for every gain combination. Fix is what real implementations do
  anyway — derivative **on the measurement**, through a first-order filter
  (`τ_d = 50 ms`). That also removes the setpoint-step derivative kick.
- **Anti-windup has to prevent the integration, not undo it.** The first
  version subtracted `error·dt` back off *after* computing `u` — by which
  point the wound-up integral had already been applied to that step's
  output. Correct form is conditional integration: while the actuator is
  pinned *and* the error would drive it further in, do not commit the
  integration at all.
- **A greedy character class ate a full stop.** The test parsed the plot's
  accessible summary with `/Steady-state error ([\d.]+)/`, which happily
  matched `0.200.` — trailing sentence period included — so `Number()`
  returned `NaN` and the assertion failed against a page that was
  completely correct. Cost about ten minutes of suspecting the physics.
  Anchored to `(\d+\.\d+)`.
- **A test compared two operating points by accident.** The steady-state
  assertion set `Kp = 10` and then switched `Ki` on, comparing against a
  `Kp = 2` baseline. At a 2 s horizon that loop is still converging (0.012),
  so the bound failed for a real reason. Integral action is now compared at
  identical Kp, which is the claim actually being made.
- A stray `serve` left running on :4173 from an earlier screenshot pass
  makes Playwright abort with "port already used" — its `webServer` block
  sets `reuseExistingServer: false` on purpose.

  robot's fitted dynamics.
